# 01. Доступ к REST API, авторизация, вебхуки, скоупы

Источники: [first-steps/access-to-rest-api.md](rest-docs/first-steps/access-to-rest-api.md), [settings/how-to-call-rest-api/authorization.md](rest-docs/settings/how-to-call-rest-api/authorization.md), [local-integrations/local-webhooks.md](rest-docs/local-integrations/local-webhooks.md), [settings/oauth/](rest-docs/settings/oauth/index.md), [api-reference/scopes/permissions.md](rest-docs/api-reference/scopes/permissions.md). Статус: *по документации*; на портале ЕС Транс не проверялось.

## 1. Условия доступа к REST

1. Платный тариф (у ЕС Транс — «Профессиональный»).
2. Подписка **BitrixGPT + Маркетплейс** — *Мой тариф → Подписка на BitrixGPT + Маркетплейс → Купить подписку*. Для проверки можно включить демо: *Мой тариф → BitrixGPT + Маркетплейс → Включить демо*.
3. Без подписки/демо REST отвечает `ACCESS_DENIED` («REST is available only on commercial plans»; у вебхука текст — «REST is available only by subscription»).

> ⚠ Условия подписки и стоимость меняются — проверять в разделе «Мой тариф» и на bitrix24.ru/prices. В базе цены не фиксируются.

## 2. Что определяет результат запроса

- **Права пользователя.** REST выполняется от имени пользователя; шире, чем в интерфейсе, не получится. Если пользователь не видит задачу в интерфейсе — через REST её тоже не получить. Для максимального доступа — учётка администратора (но см. раздел «Безопасность»).
- **Скоуп (`scope`).** Группа методов, которую разрешено вызывать вебхуку/приложению. Нет скоупа → ошибка `insufficient_scope`, метод не выполняется.
- Нужны оба условия одновременно: права пользователя **и** скоуп.

## 3. Два способа авторизации

| | Входящий вебхук | Приложение (OAuth 2.0) |
|---|---|---|
| Для чего | Свой скрипт/интеграция в одном портале | Локальное или тиражное приложение |
| Как передаётся | В URL: `https://<портал>/rest/<USER_ID>/<КОД>/<метод>` | Токен в параметре `auth`: `https://<портал>/rest/<метод>?auth=<TOKEN>` |
| От чьего имени | От создавшего вебхук | От владельца токена |
| Срок жизни | Постоянный (можно задать дату окончания) | `access_token` — 1 час; `refresh_token` — 180 дней |
| Недоступно | `placement.*`, часть телефонии, часть чат-ботов (нужен контекст приложения; ошибка `WRONG_AUTH_TYPE`) | — |

Выбор: *вебхук* — если интеграция внутренняя, один портал, не нужен интерфейс/обработчик событий; *приложение* — если нужен интерфейс во фрейме, события через `event.bind`, встройка (placement), роботы своих типов.

## 4. Входящий вебхук

**Создание:** раздел *Разработчикам → Готовые сценарии → Другое → Входящий вебхук* → в генераторе выбрать метод, проверить → указать права (скоупы) → *Создать*.
Если пункта нет — у сотрудника закрыто право: администратор открывает его в *Настройки → Настройки Битрикс24 → Безопасность → Интеграции Битрикс24 → «Кому разрешить создавать входящие вебхуки»*.

**Устройство URL:**

```
https://example.bitrix24.ru/rest/1/xxxxxxxx/department.get.json?ID=42
        └ портал          └ /rest └ user_id └ код  └ метод   └ формат └ параметры
```

**Пример (curl, POST + JSON):**

```bash
curl -X POST -H "Content-Type: application/json" -d '{}' \
  https://your-domain.bitrix24.com/rest/1/8g9l071eismy9q2l/user.current.json
```

**Правила:**
- Права вебхука = права создателя ∩ выбранные скоупы. Секретный код виден только создателю; если администратор отредактирует чужой вебхук, код обновится, а владельцем станет администратор.
- GET в адресной строке — только для быстрых проверок простых вызовов (URL попадает в историю браузера и логи). Рабочие интеграции — POST + JSON, только HTTPS.
- Только HTTPS (`INVALID_REQUEST — Https required` иначе).
- **Увольнение сотрудника:** диалог *«Сохранить интеграции и уволить»* создаёт системного пользователя (`RESOURCE_TYPE: WEBHOOK`) и переносит на него вебхуки с теми же правами; *«Отключить интеграции и уволить»* — вебхуки перестанут работать. Подробнее: [settings/system-user.md](rest-docs/settings/system-user.md).
- Сохранённый вебхук работает для любого, кто знает адрес (в том числе для уволенного) — ненужные вебхуки удалять.

> ⚠ **Практика для ЕС Транс:** привязывать вебхуки не к личной учётке сотрудника, который может уволиться, а к выделенному служебному пользователю с минимально необходимыми правами. *Это рекомендация по документации (раздел о системных пользователях и безопасности), не требование.* См. также [settings/cloud-and-on-premise/security-recommendations.md](rest-docs/settings/cloud-and-on-premise/security-recommendations.md).

## 6. Приложения и OAuth 2.0

- **Локальное приложение** — создаётся в самом портале: *Разработчикам → Готовые сценарии → Другое → Локальное приложение*. Три вида: статичное (код в браузере, своего сервера нет), серверное с интерфейсом, серверное без интерфейса. Подробно — [07-apps-and-placements.md](07-apps-and-placements.md).
- **Варианты получения токенов:**
  - *Упрощённый* — приложение открыто во фрейме Битрикс24 и получает токены при каждом открытии (`AUTH_ID`, `REFRESH_ID`). Основной случай для локальных приложений.
  - *Полный протокол OAuth 2.0* — приложение вне интерфейса Битрикс24 ([settings/oauth/index.md](rest-docs/settings/oauth/index.md)): пользователь авторизуется в портале → приложение получает `code` (живёт **30 секунд**) → обменивает на токены на `https://oauth.bitrix24.tech/` вместе с `client_id` и `client_secret`.
  - *Callback установки* — для приложений без интерфейса: токены приходят POST-ом на обработчик сразу после установки.
- **Продление токена:** `GET https://oauth.bitrix24.tech/oauth/token/?grant_type=refresh_token&client_id=…&client_secret=…&refresh_token=…`. Ответ содержит новую пару токенов и `client_endpoint` (адрес REST портала). Если приложение не обращается к порталу чаще раза в 180 дней — обновлять пару вручную по расписанию.
- `client_secret` использовать **только** на сервере в запросах к `oauth.bitrix24.tech`; в браузерный код не помещать.
- События и виджеты не работают, пока установка приложения не завершена (см. [settings/app-installation/installation-finish.md](rest-docs/settings/app-installation/installation-finish.md)).
- Если у администратора доступ к приложению открыт только отдельным пользователям — остальные получат `user_access_error`.

## 7. Скоупы (основные)

Полный список: [api-reference/scopes/permissions.md](rest-docs/api-reference/scopes/permissions.md). Самые нужные:

| Скоуп | Что открывает |
|---|---|
| `crm` | CRM (лиды, сделки, контакты, компании, смарт-процессы, CRM-формы, таймлайн…) |
| `task` | Задачи (устаревшие `tasks`, `tasks_extended`, `tasksmobile` не использовать) |
| `user`, `user_brief`, `user_basic` | Пользователи (полный / минимальный / базовый) |
| `department` / `humanresources` | Структура компании (классический / REST 3.0) |
| `bizproc` | Бизнес-процессы, роботы, RPA |
| `im`, `imbot`, `imopenlines` | Чаты и уведомления; чат-боты; открытые линии |
| `disk`, `calendar`, `lists`, `entity`, `log`, `sonet_group`, `timeman`, `telephony` | Диск, календарь, списки, хранилище данных, лента, группы, рабочее время, телефония |
| `placement` | Встройка виджетов (нужен всегда для `placement.bind`) |
| `userfieldconfig` | Настройка пользовательских полей (+ скоуп модуля, например `crm`) |
| `pull` | Push&Pull |

Принцип: выдавать **минимально достаточный** набор. Проверить, какие скоупы нужны методу, — в шапке страницы метода (`> Scope: …`). Какие методы доступны текущему токену: `scope`, `methods`, `method.get`, `access.name` (папка [common/system/](rest-docs/api-reference/common/system/index.md)).

## 8. Безопасность

- Код вебхука и токены = доступ к данным. Не публиковать, не класть в клиентский код, репозиторий, логи.
- Секреты — в `.env` (в проекте `.env` в `.gitignore`; файла-образца пока нет).
- Отзыв/пересоздание вебхука при подозрении на утечку.
- Для исходящих вебхуков проверять `auth[application_token]` в каждом запросе.
