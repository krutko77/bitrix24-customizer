# 03. Лимиты и коды ошибок

Источники: [limits.md](rest-docs/limits.md), [settings/performance/](rest-docs/settings/performance/index.md), [error-codes.md](rest-docs/error-codes.md), [_includes/system-errors.md](rest-docs/_includes/system-errors.md), [settings/oauth/error-codes.md](rest-docs/settings/oauth/error-codes.md). Статус: *по документации*. Лимиты действуют в **облаке**; значения могут меняться — сверяться со страницей лимитов.

## 1. Лимиты

### 1.1. Время одного запроса
Не более **60 секунд**, иначе таймаут. Помогает: разбивать операции, пагинация, минимум полей в `select`, вынос долгих сценариев в очередь/фон, контроль `time.duration`. Также ограничено время одного SQL-запроса внутри метода (ошибка `BITRIX_REST_V3_EXCEPTION_LIMITER_QUERYTIMELIMITEXCEPTION`, HTTP 503, заголовок `Retry-After`).

### 1.2. Интенсивность запросов (Leaky Bucket)
Каждый запрос увеличивает счётчик; при превышении порога `X` — `503 QUERY_LIMIT_EXCEEDED`; счётчик уменьшается на `Y` в секунду.

| Тариф | Y (убывание, запросов/с) | X (порог до блокировки) |
|---|---|---|
| Энтерпрайз | 5 | 250 |
| **Прочие (в т.ч. «Профессиональный»)** | **2** | **50** |

- Для ЕС Транс ориентир: **устойчиво ≤ 2 запроса/с**, кратковременный всплеск до ~50.
- Учёт — отдельно для каждого портала и **по IP источника**: несколько приложений с одного сервера делят общий лимит.
- Считаются HTTP-запросы, а не записи: 50 записей в странице, `batch` до 50 подзапросов → до 2500 записей за запрос.
- Реакция: снизить частоту, повторять с нарастающей задержкой (exponential backoff), не запускать параллельные серии с одного IP.

### 1.3. Ресурсоёмкость (`operating`)
- В `time` ответа есть `operating` (накопленное время выполнения **конкретного метода** для данного приложения/вебхука) и `operating_reset_at` (timestamp сброса самой старой минутной корзины). Окно — 10 одноминутных корзин.
- Если накопленное превысило лимит — следующий вызов этого метода блокируется: `429 OPERATION_TIME_LIMIT`. Другие методы и другие приложения не затрагиваются.
- Внешний `batch` в `operating` не считается; вложенные методы считаются по отдельности.
- Размер лимита в облаке задаёт конфигурация портала (в документации число не фиксируется; в коробке по умолчанию 420 с). **Не проверено для портала ЕС Транс.**
- Реакция: приостановить вызовы метода, первую повторную попытку планировать по `operating_reset_at`.

### 1.4. Практика
- Предпочитать `*.list` с `select` и фильтром, а не цикл по одному элементу.
- Для регулярной выгрузки больших объёмов — `start=-1` + фильтр по id ([02-rest-requests.md](02-rest-requests.md)); для аналитики — встроенный BI-коннектор (`biconnector`), а не REST.
- Вместо опроса — события / исходящие вебхуки ([06-automation-events.md](06-automation-events.md)).
- `batch` — только для связанных или небольших независимых вызовов.

## 2. Как распознать ошибку

| Тело ответа | Значение |
|---|---|
| есть `result`, `result.result_error` пуст/нет | успех |
| есть `error` (+`error_description`) | вызов не выполнен |
| `result.result_error` непустой (в `batch`) | пакет принят, часть подзапросов с ошибкой; ошибки — по ключам команд |

Статус HTTP нужен для логов, но решать по нему нельзя (в `batch` ошибки приходят со статусом 200). `error` может быть пустым — тогда смотреть `error_description` (ошибки конкретного метода: валидация параметров, объект не найден).

## 3. Системные ошибки REST (любой метод)

| HTTP | Код | Что значит / что делать |
|---|---|---|
| 500 | `INTERNAL_SERVER_ERROR` | Внутренняя ошибка. Повторить через несколько секунд; не проходит — в поддержку |
| 500 | `ERROR_UNEXPECTED_ANSWER` | Неожиданный ответ сервера. Так же |
| 503 | `QUERY_LIMIT_EXCEEDED` | Лимит интенсивности → пауза + backoff |
| 429 | `OPERATION_TIME_LIMIT` | Метод заблокирован по ресурсоёмкости → ждать `operating_reset_at` |
| 401 | `NO_AUTH_FOUND` | Нет токена/кода вебхука в запросе |
| 401 | `INVALID_REQUEST` (Https required) | Только HTTPS |
| 401 | `OVERLOAD_LIMIT` | Ручная блокировка REST из-за перегрузки — только через техподдержку |
| 401 | `ACCESS_DENIED` | REST только на коммерческих тарифах / по подписке |
| 401 | `INVALID_CREDENTIALS` | Нет активного вебхука с таким user_id/кодом (удалён, истёк, ошибка в URL) |
| 404 | `ERROR_METHOD_NOT_FOUND` | Опечатка в методе, его нет, либо нет нужного скоупа |
| 401 | `insufficient_scope` | Не хватает скоупа у вебхука/приложения |
| 401 | `expired_token` | Истёк `access_token` → продлить по `refresh_token` |
| 401 | `user_access_error` | Приложение доступно не всем пользователям |
| 403 | `PORTAL_DELETED` | Портал закрыт/удалён |
| — | `WRONG_AUTH_TYPE` | Метод требует контекста приложения, вызван вебхуком |

Ошибки сервера авторизации `oauth.bitrix24.tech` (обмен `code`, продление токена) — [settings/oauth/error-codes.md](rest-docs/settings/oauth/error-codes.md). Коды конкретного метода — раздел «Обработка ошибок» на его странице.

## 4. Шаблон обработки (JS)

```js
async function callMethod(method, url) {
  const response = await fetch(url);
  const data = await response.json();
  if ('error' in data) {            // проверяем наличие ключа, а не значение
    const err = new Error(data.error_description);
    Object.assign(err, { code: data.error, status: response.status, method });
    throw err;
  }
  const batchErrors = data.result?.result_error ?? {};
  return { result: data.result, batchErrors, hasBatchErrors: Object.keys(batchErrors).length > 0 };
}
```

Повторять автоматически только временные ошибки (`QUERY_LIMIT_EXCEEDED`, `OPERATION_TIME_LIMIT`, `INTERNAL_SERVER_ERROR`, `ERROR_UNEXPECTED_ANSWER`); остальные — исправлять причину.
