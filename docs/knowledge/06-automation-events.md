# 06. Автоматизация, бизнес-процессы, события

Источники: [bizproc/](rest-docs/api-reference/bizproc/index.md), [bizproc-robot/](rest-docs/api-reference/bizproc/bizproc-robot/index.md), [crm/automation/](rest-docs/api-reference/crm/automation/index.md), [events/](rest-docs/api-reference/events/index.md), [offline-events.md](rest-docs/api-reference/events/offline-events.md), [safe-event-handlers.md](rest-docs/api-reference/events/safe-event-handlers.md), [local-webhooks.md](rest-docs/local-integrations/local-webhooks.md). ## 1. Карта инструментов автоматизации

| Задача | Инструмент | Код? |
|---|---|---|
| При смене стадии сделать действие внутри портала (задача, письмо, смена поля, уведомление) | **Роботы CRM** (настраиваются в интерфейсе: карточка → Автоматизация) | нет |
| Согласование, многошаговый процесс с заданиями людям | **Бизнес-процесс** (дизайнер БП) / умный сценарий | нет |
| Внешний сигнал должен двинуть сделку по стадиям | **Триггер «Отследить входящий вебхук»** + `crm.automation.trigger` | минимально (один HTTP-вызов) |
| Внутри робота/БП вызвать свою систему и вернуть результат | **Робот приложения** (`bizproc.robot.add`) | да, нужно локальное приложение |
| Узнать во внешней системе, что объект создан/изменён | **Исходящий вебхук** или **подписка `event.bind`** | да, публичный обработчик |
| Запустить БП из внешнего скрипта | `bizproc.workflow.start` | да |
| Забирать изменения, когда нет публичного URL (файрвол) | **Офлайн-события** (`event.offline.*`) | да, нужно приложение |

> Первым делом проверять, решается ли задача штатными роботами/БП — без кода. REST подключать, когда нужна связь с внешней системой.

## 2. Роботы приложений

Робот приложения — шаг в автоматизации (CRM, БП, умные сценарии), который вызывает **обработчик вашего приложения**.

- Регистрация: [`bizproc.robot.add`](rest-docs/api-reference/bizproc/bizproc-robot/bizproc-robot-add.md) (скоуп `bizproc`, **только администратор**, **только в контексте приложения**, вебхуком нельзя). Обязательные параметры: `CODE` (символы `a-zA-Z0-9.-_`; уникален среди роботов *и* действий приложения), `HANDLER` (http/https, в имени хоста должна быть точка), `NAME`. Прочее: `PROPERTIES` (входные параметры), `RETURN_PROPERTIES` (выходные), `USE_SUBSCRIPTION` (`Y` — ждать ответа), `AUTH_USER_ID`, `DESCRIPTION`, `DOCUMENT_TYPE` и др.
- Группа методов: `bizproc.robot.add / update / delete / list`, `bizproc.event.send`.
- Ожидание результата: `RETURN_PROPERTIES` + `USE_SUBSCRIPTION='Y'` → Битрикс24 шлёт POST на `HANDLER` (через сервер очередей, `application/x-www-form-urlencoded`) с `workflow_id`, `code`, `document_id`, `document_type`, `event_token`, `properties` и `auth` → приложение считает результат → возвращает его в процесс через **`bizproc.event.send`** с `EVENT_TOKEN`; пояснение в журнал процесса — `LOG_MESSAGE`.
- «Действия приложений» (`bizproc.activity.*`) — близкая по модели сущность для дизайнера БП. Для новой разработки рекомендуются **роботы** (работают и в CRM-автоматизации, и в БП, и в умных сценариях).

## 3. Бизнес-процессы через REST

- Запуск: `bizproc.workflow.start` — нужны `TEMPLATE_ID`, `DOCUMENT_ID` (например `['crm','CCrmDocumentLead','LEAD_1']`) и входные параметры шаблона.
- Контроль: `bizproc.workflow.instances`, остановка `bizproc.workflow.terminate`/`kill`.
- Шаблоны: `bizproc.workflow.template.add/update/delete/list` (администратор).
- Задания людям (согласование/ознакомление/ввод данных): `bizproc.task.*`.
- Активный процесс использует **копию шаблона на момент старта** — правка шаблона не влияет на уже запущенные.
- Туториалы: [tutorials/bizproc/](rest-docs/tutorials/bizproc/index.md) (кастомное действие, настройка робота, массовая остановка процессов).

## 4. Триггеры и автоматизация CRM

- **Готовый webhook-триггер** («Отследить входящий вебхук» в автоматизации CRM): берём `code` из URL триггера → `crm.automation.trigger` с `target` (формат `DEAL_25`) и `code`. Триггер надо заранее привязать к стадии в интерфейсе.
- **Триггеры приложения:** `crm.automation.trigger.add / list / execute / delete`.
- Робототехника CRM в интерфейсе: [helpdesk — Роботы в CRM](https://helpdesk.bitrix24.ru/open/24367166/), [Триггеры](https://helpdesk.bitrix24.ru/open/24473054/).
- Умные сценарии (последовательность роботов): [smart-scripts-installation.md](rest-docs/settings/app-installation/smart-scripts-installation.md).

## 5. События: общая модель

Событие = уведомление «что-то изменилось» (`ONCRMDEALADD`, `ONCRMDEALUPDATE`, …). Подписка — на **URL-обработчик**.

Как это работает:
1. Подписка: `event.bind` (приложение) или исходящий вебхук (интерфейс).
2. Пользователь/система меняет данные.
3. Событие попадает в **очередь на сервере очередей**, оттуда на ваш URL уходит POST.

Следствия:
- Обработчик вызывается **не мгновенно и не напрямую**; при медленных ответах сервер **снижает частоту** вызовов (интервалы растут). Отвечать быстро (принять → 200 → обработать асинхронно).
- URL должен быть публичным HTTPS с валидным сертификатом, без `localhost`/локальных адресов. Адреса сервера очередей, которые нужно пускать через файрвол, — [network-access.md](rest-docs/settings/cloud-and-on-premise/network-access.md).
- В событии обычно только **ID объекта** (`data[FIELDS][ID]`) — полные данные запрашивать методом (например `crm.item.get`).
- Все значения приходят **строками** (`application/x-www-form-urlencoded`).
- Приложение: события не идут, пока установка не завершена.

### Способы подписки

| | Исходящий вебхук | `event.bind` (приложение) |
|---|---|---|
| Где настроить | *Разработчикам → Готовые сценарии → Другое → Исходящий вебхук* | REST из кода приложения |
| События | Только онлайн-события из списка | Все, включая офлайн-события |
| Кто может | Администратор | Админ; обычный пользователь — только онлайн и только на себя (`auth_type`), иначе `ACCESS_DENIED` |
| Вебхуком | — | `event.bind` через **вебхук не работает** → `WRONG_AUTH_TYPE` |
| На демо-режиме | Недоступен | — |

`event.bind` параметры: `event` (код, должен входить в скоуп приложения, иначе `ERROR_EVENT_NOT_FOUND`), `handler` (URL; точка в имени хоста), `auth_type`, `event_type` (`online`/`offline`), `auth_connector`, `options` (напр. `minTimeout` для `ONOFFLINEEVENT`). При удалении приложения подписки удаляются, при обновлении сохраняются. Список доступных событий: метод [`events`](rest-docs/api-reference/events/events.md); отписка — `event.unbind`; список подписок — `event.get`.

### Что приходит в обработчик (исходящий вебхук)

```
event=ONCRMDEALUPDATE
data[FIELDS][ID]=662
ts=1724140800
auth[domain]=example.bitrix24.ru
auth[member_id]=…
auth[application_token]=…
```

Для приложения в `auth` дополнительно — `access_token`, `refresh_token`, `scope`, `client_endpoint` и т. д., плюс `event_handler_id`.

### Проверка подлинности
Сравнивать `auth[application_token]` с сохранённым токеном (у исходящего вебхука он показан в форме — поле «Токен приложения»; у приложения приходит в `ONAPPINSTALL`, обновляется при `ONAPPUPDATE`). Несовпадение → запрос не доверенный. Особенно важно в `ONAPPUNINSTALL`, куда авторизация не передаётся. Подробно — [safe-event-handlers.md](rest-docs/api-reference/events/safe-event-handlers.md). Проверка доступности обработчика — [test-handler.md](rest-docs/api-reference/events/test-handler.md).

### Офлайн-события
Для приложений, которые не могут принимать входящие вызовы (файрвол, внутренняя сеть). Битрикс24 складывает изменения в **очередь**, приложение само забирает их `event.offline.get` (с `clear=1` — очистка, либо резерв пакета с `clear=0` и последующая очистка), `event.offline.list`, `event.offline.clear`, `event.offline.error`.
- В очереди **не история, а текущее состояние**: сделка, изменённая 1000 раз, даст одну запись (ключ `MESSAGE_ID` = хеш имени события и данных).
- Доступны только приложению; регистрация с `event_type=offline` — только администратор.
- `auth_connector` создаёт отдельную очередь, в которую не попадают изменения, сделанные самим приложением (защита от эха).

## 6. Типичные схемы для ЕС Транс (шаблоны решений)

*(черновые идеи по возможностям платформы; применимость к процессам компании не обсуждалась — см. [../gaps.md](../gaps.md))*

1. **Сделка → внешняя система:** исходящий вебхук `ONCRMDEALUPDATE` → обработчик получает `ID` → `crm.item.get` по вебхуку → отправка во внешнюю систему.
2. **Внешняя система → сделка:** вебхук-скрипт `crm.item.add`/`update`, при смене статуса — `crm.automation.trigger`.
3. **Нужна логика внутри робота:** робот приложения + обработчик на своём сервере + `bizproc.event.send`.
4. **Нет публичного адреса у сервера:** офлайн-события + периодический `event.offline.get`.
