## Сейчас в работе
**Активных задач нет.** Задачи A и B закрыты; новые сотрудник поставит по мере появления.

**Задача A (номер счёта → карточка Заказа) — ЗАКРЫТА 2026-11-20.**
- Суть: при изменении счёта (штатный СП «Счета», создаётся из сделки воронки «ЗАКАЗЫ») номер из 1С попадает в **множественное** поле сделки «Номер счета к этому Заказу»; счетов на заказ несколько.
- Как устроено (по экспортам БП): в БП «Счета. [KG] При изменении» номер из «НОМЕР 1С техническое» режется `explode("-")`, берётся часть с ключом 1, переменная типа «Число» убирает ведущие нули; результат пишется в «Номер счета для шаблона техническое» и в заголовок счёта (TITLE); затем без ожидания запускается БП **932** с параметром `accountNumber` (строка, необязательный). Формат номера 1С всегда «ПРЕФИКС-ЧИСЛО» (подтвердил сотрудник); потеря ведущих нулей — сознательная.
- **Причина дублей и решение:** 932 запускался при каждом изменении счёта и без проверки дописывал номер. Теперь в 932 перед записью стоит «Условие»: параметр `accountNumber` заполнен И поле «Номер счета к этому Заказу» **не содержит** `{=Template:accountNumber}` → «Изменение документа» с «Дополнить множественные поля = да»; иначе — ничего. Правку внёс сотрудник вручную (сверена по скриншотам), протестировал — «всё работает». Подтверждено на уровне «всё работает»; детали теста (строка «15» → «5», т. е. точное совпадение элемента, а не подстрока) не уточнялись.
- Сотрудник **удалил** блок 1 БП «При изменении» (галочка «есть в Заказе» — был мёртвым кодом) и лишнее поле-дубль «ID счетов к Заказу техническое».
- Остаточный риск (не проявлялся): 932 запускается без ожидания — при серии очень быстрых изменений одного счёта от 1С два экземпляра могут одновременно прочитать поле (read-modify-write).
- Подробности, коды полей и схемы — **`docs/local-task-invoice-number.md`** (локально, вне git). Экспорты `bp-910.bpt`, `bp-932.bpt` лежат в корне репозитория (**публичного**, сотрудник сам их выложил и решил оставить; ключей и URL внутри нет, но они раскрывают структуру полей).
